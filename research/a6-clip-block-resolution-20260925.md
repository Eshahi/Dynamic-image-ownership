# A6 CLIP visual-path resolution on the protected Windows host

Status 2026-09-25: **the A5-required image encoder has a reusable, offline, fail-closed local adapter.** The full upstream `clip` package and its text tokenizer are still blocked by Windows Code Integrity. This is a resolution for the *image-only method dependency*, not a resolution of the unrelated native `regex` binary's trust status. A6/issue #7 and draft PR #58 remain open for complete numerical, image-conditioned gradient, environment and resource evidence.

## Why this path is within the method

The [A5 method specification](method-spec.md) defines its semantic feature as `encode_image(CLIP_preprocess(X))` with official `openai/CLIP` ViT-B/32 and a fixed source/checkpoint identity. It does not call `clip.tokenize` or `encode_text`; Stable Diffusion's separate fixed empty-string conditioning uses that model's own tokenizer. The [official CLIP code at the pinned commit](https://github.com/openai/CLIP/blob/d05afc436d78f1c48dc0dbf8e5980a9d471f35f6/clip/clip.py) imports `SimpleTokenizer` eagerly when the package loads, and [its tokenizer](https://github.com/openai/CLIP/blob/d05afc436d78f1c48dc0dbf8e5980a9d471f35f6/clip/simple_tokenizer.py) imports native `regex`. That eager import blocked the original A6 synthetic visual preflight, not the image encoder's execution itself.

`scripts/a6_clip_visual.py` loads only the hash-checked official `clip/model.py` visual builder, the exact official ViT-B/32 JIT checkpoint, and the official `clip.py` image preprocessing operations. It never imports `clip.__init__` or the unused tokenizer, calls no network downloader, and refuses other checkpoint sizes/digests or source changes. It returns an `encode_image`-capable model and transform for later reviewed method integration. It does not change or execute the native `regex` binary and does not disable or alter any Windows security setting. This is a project-owned adapter around **official source and weights**, not a new CLIP model or an altered scientific method. Study-image execution is still subject to the runner's exact-manifest user approval.

An independent review found a hash-then-reopen race in the initial adapter. The subsequent bounded fix consumes in-memory snapshots of the exact verified source and checkpoint bytes rather than reopening their paths; [review and post-fix runtime evidence](a6-clip-adapter-review-20260925.md) are recorded separately. The project float32 CUDA feature profile follows A5 but is not upstream CLIP's default CUDA fp16 result.

The installed Windows CLIP wheel uses CRLF line endings while the pinned upstream files use LF. GitHub's public content API for commit `d05afc436d78f1c48dc0dbf8e5980a9d471f35f6` returned `clip/clip.py` SHA-256 `9540f200fbf8145479fa655382a56dab048d238cc698b9cbd8df3b6d86d3f1b6` and `clip/model.py` SHA-256 `9902cbe5ee90a1da2aa3e6f043e8a23dc1f8831193b963785c9af03d5c7bef2c`. Only replacing CRLF with LF in the installed files yielded exactly those two official digests. The adapter enforces both the installed exact-byte digests and normalized upstream digests before executing source. This resolves the apparent A5-versus-A6 source-hash discrepancy as line-ending conversion, not a code-content change; it does not independently authenticate a future checkpoint or package without the runtime checks.

## Verification and boundary

- After extraction into the adapter (commit `2f72a850e06408e54809afc59a4cfc0975c845b6`), a second bounded offline synthetic CLIP invocation exited 0 under the existing external 1,200-second timeout. Its CPU/CUDA feature digests, preprocess digest and maximum normalized component difference `1.8790364265441895e-05` **exactly matched** the earlier direct-source preflight in [the visual receipt](a6-clip-visual-runtime-receipt-20260925.md). The new ignored stdout SHA-256 is `b4c77638e8a4372685521d9b5a1af93c797791486ed3f6521f67dc9f8c959d58`; stderr was empty with SHA-256 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.
- The workflow Python suite discovered 87 tests: 83 passed, four environment-dependent skips. The isolated science venv ran all five adapter tests, including real installed-source verification and the exact preprocessed synthetic tensor fingerprint; all passed. Tests cover changed source rejection before code execution, invalid device, wrong checkpoint size and LF/CRLF normalization.
- No study image, dataset, diffusion inference, complete method gradient, paid resource or Spec Kit transition was used. This does not establish scientific CLIP/CPU/CUDA parity over a real evaluation set, full environment reconstruction or A6 completion.

## Full package access, if later required

Read-only host checks found Smart App Control's `VerifiedAndReputablePolicyState=1`; Code Integrity events 3077/3033 identified the unsigned `_regex.cp312-win_amd64.pyd` block, and `CiTool --list-policies --json` returned access denied. Microsoft's [Smart App Control FAQ](https://support.microsoft.com/en-us/windows/security/threat-malware-protection/smart-app-control-frequently-asked-questions) states that there is no per-app exception and recommends a valid developer signature for blocked code; its [developer overview](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview) explains signing/reputation criteria. Disabling protection is not necessary for the A5 visual path and was not done. If a future reviewed requirement actually needs CLIP text APIs, seek a properly signed trusted binary from its maintainer or use a separately approved compute environment where this host policy does not apply; do not silently replace the tokenizer, evade Code Integrity, or infer paid-VM authorization from this adapter.
