# Candidate sheets and interpretation

The individual C01–C21 sheets are the assessed candidates; raw proposals live in ../ideas/. The three author bundles there preserve the initial sheet assessments. Only the consolidated ../05-candidate-table.md determines the final shortlist. Repeated appearances of a candidate in a bundle and an individual sheet count once.

Screening follows ../05-screen-rule.md, committed at dbf4dcd before scoring. Its SHA-256 is `df774bae6ae4d62b8e37f1f2f2058d4a87170e30708b795daa03423b0397f799`. Scores are ordinal judgments, not probabilities. The independent forecasters in WP6 receive evidence and defined events rather than these scores.

All candidates are prospective. A <=20-hour first test usually checks a necessary source of advantage: action-dependent headroom, useful history or a secure feasible operating point. Passing such a test would not establish RL superiority, excluded-family transfer, publication readiness or a completed full campaign. A cap with unknown runtime permits RESOURCE_STOP; it is not evidence that the test will finish.

Data acquisition follows ../ideas/fresh-data-contract.md and each sheet's stated counts. No data is acquired in this session. Nothing changes the frozen F6 run. All costs use the retained instance price as a planning conversion, not a current rental quote or spending authorization. Detector access, payload, C/J semantics, strict clean quality and attack-output fidelity must remain explicit when comparing sheets.

Benefits are classified separately: direct defense, diagnostic/resource efficiency, security discovery, and article evidence. Only a direct defense improvement under the fixed quality/binding contract can satisfy WP6 A2. A discovery that a defense can be broken is useful security evidence but cannot be counted as better defensive C/J.
