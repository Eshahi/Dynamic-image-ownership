# Synthetic harness Windows process containment

Scientific candidate remains **UNRESOLVED**. This is a stdlib infrastructure amendment to the generated-JSON harness, not an official rehearsal, approval, held-out evaluation or GPU readiness verdict.

`scripts/m1_windows_job.py` creates a private Windows Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE and no breakaway flags. The Job handle is noninheritable. It creates exactly its own child using CreateProcessW with CREATE_SUSPENDED, CREATE_NO_WINDOW and STARTUPINFOEX. The explicit inherited handle list contains only a duplicated log handle and NUL stdin; it does not include the Job or unrelated host handles. The child cannot execute Python or scientific instructions before AssignProcessToJobObject succeeds, IsProcessInJob confirms assignment, and the ownership receipt is written. Only then is the primary thread resumed. An assignment error fails closed and terminates the exact never-resumed child handle; there is no uncontained Popen fallback.

Normal child exit, timeout, exception and interruption close the Job. Closing the last handle kills assigned descendants, including grandchildren and venv-launcher interpreter descendants. Parent process death also closes its private Job handle at the kernel level. Closing one Job does not kill another Job's child. No process-name search, PID enumeration, shell taskkill or outside-process adoption is used. The class only owns handles returned from its own CreateProcessW call. An external callback receives creation/assignment/running receipts with a unique Job identifier, parent PID, exact command and own child PID before any termination path.

The harness now journals containment receipts per attempt and adds the helper's byte SHA-256 to the recovery fingerprint. It closes the Job after each completed unit and in final cleanup, even if the root has already exited. Existing synthetic-only checks, explicit recovery, stale-lock refusal and UNRESOLVED/NOT_EVIDENCE labels remain unchanged. A Windows host that refuses nested Job assignment is unsupported and fails closed; this implementation does not weaken isolation to proceed.

Six real Windows CPU tests create only token-bound fixture processes under temporary test directories. Their exact recorded PIDs are opened solely for observation after verifying token and parent relations; termination targets the test's own stored handles/Jobs. Tests cover: no worker marker before verified suspended assignment; timeout and interruption kill root/child/grandchild; assignment failure never starts the child; a separate test-owned Job survives another Job's close; and hard launcher termination closes its inner Job and kills descendants while the outer Job remains open. Eleven existing synthetic harness tests also pass. A Windows venv python.exe can introduce an intermediate launcher; exact-PID fixtures use the base interpreter, while the production helper contains the full inherited process tree.

These tests exercise process containment and JSON lifecycle primitives only. They do not certify official same-commit generated-image rehearsal stages, model cleanup, GPU driver behavior, storage pressure, distributed execution, OS shutdown durability or scientific adequacy. Hard interruption can still leave a stale harness lock or inconsistent journal receipt; those directories remain preserved and require explicit reviewed recovery. No lifecycle gate or approval record was modified, and no unrelated process was terminated.
