Official evidence: [PyTorch2.7 release](https://pytorch.org/blog/pytorch-2-7/) explicitly adds Blackwell and CUDA12.8 wheel support; [official previous versions](https://pytorch.org/get-started/previous-versions/) pairs torch2.7.1 and torchvision0.22.1 with cu128. [PyTorch2.7.1 reproducibility source](https://github.com/pytorch/pytorch/blob/v2.7.1/docs/source/notes/randomness.rst) warns that cross-platform/release reproducibility is not guaranteed. This is official compatibility support, not an empirical test of our server/environment.

Recommend Python3.11 Linux, torch2.7.1/torchvision0.22.1 from the official cu128 index, diffusers0.35.1, transformers4.49.0, huggingface-hub0.34.4, accelerate1.10.1, peft0.17.1, safetensors0.6.2, numpy1.26.4, scipy1.15.3, Pillow11.3.0, lpips0.1.4. For WAM preserve its pinned requirements: omegaconf2.3.0, einops0.8.0, timm1.0.11, opencv-python4.10.0.84, scikit-image0.24.0, scikit-learn1.5.2, pycocotools2.0.8. Include requests/tqdm/regex/ftfy for actual local imports and OpenAI CLIP preprocessing, jsonschema for manifests; pin their resolved versions in the installation lock. Sentencepiece/protobuf are needed for optional T5/FLUX/KD tokenizer paths, not SDXL's CLIP-only path. No invisible-watermark, xformers, quantizers, torch.compile or training frameworks are required by the core.

These are **proposed direct pins**, not a tested complete transitive lock. Parent must freeze the actual dependency file and verify CPU imports/adapter API compatibility before labeling code ready. diffusers0.35.1 setup requires hub>=.34 and peft>=.17 when PEFT is installed. VINE imports peft.LoraConfig even though its selected no-LoRA constructors do not train/use LoRA. Never install the obsolete paper environment over a cu128 runtime. v0.36.0 (release2025-12-08) was screened; the core classes already exist in0.35.1, so newer pipeline additions supply no scientific reason to change the audited core version. Do not claim0.35.1 is latest.

VINE's released constructor actually initializes **stabilityai/sd-turbo**, not SDXL-Turbo. T3 pins code/encoder/decoder/dependency snapshots and licenses. Inspection here independently confirms tokenizer/CLIP, UNet, VAE and DDPM scheduler nested load calls. Offline path substitutions must cover all of them. Native VINE/WAM inference is FP32 and must not inherit R1 autocast; use their native residual resizing and distinct PNG quantization per T3. Keep full SD-Turbo fp32 dependency weights in the download plan, even though learned VINE tensors overwrite portions; config-only construction is not verified equivalent.

Determinism: set CUBLAS_WORKSPACE_CONFIG=:4096:8 before CUDA initialization, cudnn.benchmark=False, cudnn.deterministic=True, torch.use_deterministic_algorithms(True), disable CUDA matmul/cuDNN TF32, record float32 matmul precision and SDPA backend. Seed Python/NumPy/global torch for any incidental code and supply the fresh per-call CUDA generator for pipeline sampling. Record deterministic-operation failures explicitly; do not silently switch to warn_only or another attention implementation after observing scores. For strongest fixed-device reproducibility a frozen SDPA math backend is possible but slower/more memory intensive; whichever backend parent selects must be fixed and recorded before outcomes. Exact equality across old/local/server GPU releases is not promised.

Memory: one-image batches; load/embed one baseline at a time, save marks, release it; execute one regenerator at a time; CPU CLIP/LPIPS scoring as existing adapters. Full fp32 VAE1024 decoding increases peak VRAM. Prefer24GB or larger and reserve host RAM for loads; this is planning, not measured sufficiency. `enable_model_cpu_offload` with accelerate is a legitimate predeclared fallback, not quantization; must be integrated carefully with explicit VAE casting. Do not combine manual `.to('cuda')` and device-map/offload hooks ad hoc. No VAE tiling: it changes spatial context/output and would create another attack. OOM should trigger the fixed offload/retry policy, with missingness if exhausted, not reduced resolution or precision. Stage2 must verify CUDA runtime, GPU capability, host driver and tiny synthetic numerical operations before any real mark. Driver release minima were not verified by accessible NVIDIA source here.

## FLUX and Kandinsky3

[FLUX official metadata](https://huggingface.co/api/models/black-forest-labs/FLUX.1-schnell) reports gated=auto at741f7c3ce8b383c54771c7003378a50191e9efe9. R2/D2 therefore disabled under brief. [Pinned FLUX img2img code](https://github.com/huggingface/diffusers/blob/v0.35.1/src/diffusers/pipelines/flux/pipeline_flux_img2img.py) constructs sigma linspace(1,1/N,N), applies scheduler's resolution-dependent shifting, then truncates. At10 requested steps .1/.2/.4 retain1/2/4 steps. VAE posterior is sampled, shift/scaling applied, then flow noise added. guidance0 for schnell is not SD-style CFG: model guidance embedding flag determines whether it is consumed. True CFG in this implementation is separate. No numerical sigma values are frozen because the gated scheduler config was not retrieved. Do not infer DDIM strength equivalence.

[Kandinsky3 v0.35.1 code](https://github.com/huggingface/diffusers/blob/v0.35.1/src/diffusers/pipelines/kandinsky3/pipeline_kandinsky3_img2img.py) independently verifies T2's proposal: native MoVQ encode returns continuous `.latents`; actual __call__ passes those four-channel tensors to prepare_latents, bypassing the generic dormant posterior-sample branch. Native DDPMScheduler adds stochastic denoising noise. Decode calls force_not_quantize=True. At20 steps strengths retain2/4/8, but beta schedule/corruption differ from R1. Diagnostic must encode/decode continuous latents, no posterior mode and no codebook quantization or SD scaling. Keep this proposal separate; ~28GB selected KD3 weights alone cannot simply be added under the global30GB cap. T2's download plan is the source for exact cost/storage, and optional prompt embeddings must carry their attention mask. Never silently swap in KD3 for failed FLUX availability.
