## Correct the nominal-strength trap

The pinned FLUX and SD3 img2img functions use `t_start = int(max(N - N*strength, 0))`, giving `ceil(N*strength)` updates for positive strength, subject to arithmetic at boundaries. With FLUX N=4, strengths .1, .2 and .25 all select one update; .4 and .5 select two. The earlier WP1 suggestion of zero updates below .25 was incorrect for this pinned implementation. Only zero strength has no updates and is rejected. Do not pay for duplicate cells or interpret duplicates as a flat dose-response curve.

FLUX's raw four-step sigma grid is [1,.75,.5,.25], but released scheduler shifts can transform it. Anonymous access to the exact gated scheduler configuration failed. Therefore the actual shifted grid is **unverified**, despite source-level knowledge of how it will be computed. For example, under dynamic exponential shifting with the default 1024px token-count parameters, raw .25 would become approximately .512844; with fixed shift=1 it remains .25. Neither conditional value is asserted as the released checkpoint's actual setting.

For flow interpolation the forward state is `(1-sigma) z + sigma epsilon`; for the established DDIM it is `sqrt(alpha_bar) z + sqrt(1-alpha_bar) epsilon`. Compare the actual affine coefficients, scaled encoder displacement, complete reverse response and achieved image fidelity. Equal numeric strength, sigma or update count alone is not matched severity. The [severity contract](analysis/severity-contract.md) derives this distinction and specifies source-paired reference handling.

The following is a design choice made before any FLUX output, not a new attack search:

Use pinned v0.35.1 native FluxImg2Img, the audited model revision **741f7c3ce8b383c54771c7003378a50191e9efe9**, 1024px native input, frozen Lanczos 512→1024→512 preprocessing, empty prompt and prompt_2, guidance_scale=0, true_cfg_scale=1, max_sequence_length=256, batch one, native posterior sampling, no quantization or extra watermark save helper. Preserve native scheduler flags. Use seeds 12/13/14 and fresh native generators per call.
2. Before outputs, read the authorized model's configuration and record actual schedule arrays. Candidate strengths are **.25, .50, .75** with four scheduled steps; verify three distinct suffixes. Do not add custom sigmas, extra steps or per-arm settings. If the release does not match the source-level interface, stop that optional adapter as unsupported rather than silently changing the model.
3. On the existing 60 development sources and four marked arms only, use exactly WP3's fidelity target and 80% per-arm source/output requirements. Select the largest worst-arm mean clipped LPIPS score, with ties choosing fewer model updates then lower strength. No target-detector output, original-source quality or F5-specific preference enters selection. Record ineligibility if none passes.
4. Complete detector-free resource and derivative support checks before full development. Allocate the cutoff and maximum GPU-hours in WP5. A failure activates the declared fallback; it does not authorize a larger machine, extra spending, new precision or new schedule without the relevant future approval.
5. Exclude the selected optional family and Kandinsky from fitting kappa, q90 and the quality-only comparator. Its Phase-A outputs can be used for quality-only operating-point selection and implementation checks. The family remains excluded from model fitting/calibration; it is not an entirely unobserved model because its design and quality were inspected.
6. After all settings are frozen, generate the fresh-source challenge and its C0 control with paired explicit randomness for the mechanism evaluator. Preserve a separate posterior-mode codec-only cell. This auxiliary cell does not share the native sampled-posterior convention and is not a matched-isolation proof by itself.

If no quality-eligible FLUX suffix exists, report that native few-step family as quality-ineligible. The existing Kandinsky .2 fallback remains fixed, without searching its strength against detection. If its achieved quality misses the region, retain a descriptive challenge with that limitation. Core H1–H3 and the R0/R1 law test do not disappear when the optional family fails.

## Resources and the user's exact decision

FLUX's 23.78 GB transformer is approximately 22.15 GiB before activations. Moving a whole transformer onto a 24 GiB 4090 does not establish fit merely because other modules are offloaded. Prefer batch one with a **48 GB GPU**, at least **64 GB RAM** and **150 GB disk**, inactive-module offload and cached text embeddings. Actual peak memory and derivative feasibility must be measured on the future server; those specifications are planning requirements, not a benchmark. Do not substitute quantized weights to rescue a run after outcomes.

Download only one representation: transformer 23.78 GB, T5 9.52 GB, CLIP .246 GB and converted VAE .168 GB, plus small files. The old 30 GB total-download allowance is smaller than this optional family alone. The final approval request must explicitly cover a larger study download ceiling if FLUX is retained, as well as the combined core models, disk and transfer time. No implicit amendment is made here.

If the user chooses FLUX, they must personally sign in to the intended Hugging Face account, open [the official FLUX.1-schnell page](https://huggingface.co/black-forest-labs/FLUX.1-schnell), review its current conditions and accept the requested information-sharing agreement if willing. Later authenticated server access must use a private credential mechanism; no token belongs in a report or committed file. Default: **no acceptance and no download**. A refusal uses the explicitly disclosed Kandinsky fallback. SD3.5 has its own gate and does not remove this decision.

The main scientific consequence is bounded: a new family adds external-validity evidence only if a usable operating point and the forecast computation both exist. Missing access, excessive resources, unsupported derivatives or an overly coarse native schedule are legitimate limitations, not evidence for or against the transfer law.
