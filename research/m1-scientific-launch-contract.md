Version `m1-scientific-launch-contract-v1`, 2026-10-04. Prospective design by gpt-6-astra/xhigh. This specifies the remaining integration for the conditional A-C end-to-end candidate; it is not an execution approval, source adoption, capability, completed rehearsal or M1 verdict. No held-out bytes, annotation values or features were inspected. No executable, retained output, official runtime or shared state is changed by this document.

## Decision and current boundary

Use the installed official dispatcher unchanged, with a reviewed scientific **launcher** as its `reviewed_script`. The launcher verifies the official envelope, an actual externally recorded human approval, and the applicable real source/scope decisions; only then may its private raw broker issue scoped reads to its owned scientific child. `issue_scientific_capability` remains deny-default until this complete path is implemented and tested. Generated rehearsals use the same candidate, broker protocol, child containment, journal and recovery logic, with a separate fixture issuer that cannot authorize acquired data.

Prepare all code, metadata, exact manifests, bounded recovery alternatives and candidate-identical rehearsals before M1. Present one concrete package for the user's confirmatory decision after the independent M1 review. The package must disclose the narrow COCO512 scope, actual selected candidate and negative development findings, fixed thresholds, source/annotation adoption, owner/seed amendment, resource ceilings and recovery allowance. A-C remains conditional on the ongoing development expansion and threat assessment; this contract does not select it on incomplete evidence.

The exact scientific child interface from the official dispatcher is:

`[sys.executable, reviewed_script, "--manifest", <output>/execution-manifest.json, "--output-dir", <output>]`.

There is no forwarded approval argument, arbitrary candidate argument list or environment field. The dispatcher writes `execution-manifest.json` and a running outer `manifest.json` **before** launch. The latter contains `approval_reference=object_digest(approval)` and `execution_manifest_sha256=object_digest(execution_manifest)`. It creates a fresh `<artifact_root>/<stage_id>/<run_id>` and four contract directories. It owns these outer records; the scientific launcher writes distinct declared artifacts inside them, never overwrites the outer manifests, and never treats a fixture's empty-output shortcut as a scientific envelope.

`approval_check` validates schemas and exact experiment/run/target, canonical manifest digest, approve decision, `timestamp <= now < expires_at`, and duration/USD ceilings. It does **not** authenticate the author of `actor`/`source_ref`, accept a source contract or implement checkpoint recovery. `object_digest(x)` is SHA256 of UTF-8 `json.dumps(x, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)`; use that implementation rather than a pretty-file hash.

Even preview verifies every declared input's contained path and bytes. Execution additionally checks exact clean Git HEAD, tracked reviewed script, and available local GPU resources. Thus all official `inputs` must be contained **metadata/code/config receipts**; external image/annotation members are not followed in preparation or preview. Local execution uses `subprocess.run` with a deadline, not a descendant-process sandbox. The reviewed owned-Job launcher is still necessary. The sanitized environment removes arbitrary flags: initialize the frozen deterministic execution settings inside the reviewed child before CUDA/model initialization, and record their actual values.

## Authentic decision and source-adoption join

Use a fixed external decision-store lookup keyed by the **canonical execution-manifest digest**, for example the reviewed lookup rule `<trusted_decision_root>/<digest>/approval.json`. This is a prospective location rule, not a file created here. It avoids trying to put the approval's hash into the manifest that the approval itself hashes. The launcher accepts no caller-supplied replacement approval path. The actual human or authenticated decision controller supplies records after the exact M1 decision; an agent does not generate an approval JSON, set a true flag, or transcribe a hypothetical verdict to satisfy a test.

The trust adapter must verify the decision's origin through the configured authoritative record/access boundary, then call the installed `approval_check` unchanged. Its output binds the exact authenticated source reference and actor, approval digest, approved packet/core/source-contract/schedule/index identities, permitted attempt set, expiry and aggregate ceilings. A trusted store entry can be a read-only record of an authenticated controller/user action; merely naming a writable directory `trusted`, hashing a JSON file, or asserting `actor="user"` is insufficient. The store's actual provisioning, access policy and source-reference resolution are implementation prerequisites, not assumed existing capabilities of `approval_check`.

Require equality among:

- actual canonical execution digest, the authenticated approval's `manifest_sha256`, and the dispatcher's `execution_manifest_sha256`;
- canonical approval digest and the dispatcher's `approval_reference`;
- run/experiment/stage/target/clean commit and the approved attempt plan;
- launcher-observed config/core/index/schedule/source-contract hashes and the identities explicitly covered by the decision.

Independently verify the applicable real source/scope acceptance. The inspected lifecycle has `scope-acceptance` and `plan-acceptance`, not a special ready-made source-adoption gate. Use their genuine evidence/decision chain only if it covers this exact source contract and narrow amendment. `control.status`, its workflow hash and consumed decision archive can establish what the actual controller recorded; a generic old `approve` for another evidence package cannot. Gate transitions require the real controller with the applicable current-state fingerprint and actual authority. Do not manufacture a completed step, invent a new gate name, replay a stale decision, or manually edit `.specify` state.

The adoption verifier must return an evidence-derived result identifying the controller run/workflow, relevant step IDs and decision hashes, evidence package/source-contract digest and authority/source reference. If the necessary mapping is unsupported or the real transition has not occurred, return `pending_source_adoption`, with raw access denied. It is a preparation dependency to resolve through the actual controller, not a request for a per-step user review and not a reason to stop other development. Delegated technical acceptance must name the actual agent/delegation if that is what occurred; only the user's real M1 decision authorizes held-out compute. The final single decision may explicitly adopt the narrow source/scope/seed amendments and authorize the listed compute batch together; the controller records its applicable transitions without inventing extra human decisions.

These controls protect scope and provenance under trusted reviewed code and host access controls. Current official JSON, private Python objects and receipt hashes do not constitute cryptographic protection against malicious same-user Python or a forged host. No such security claim is required or made. An official output envelope is an integrity join, not independent proof of who launched the process. Scientific direct invocation without both the genuine decision/adoption chain and exact envelope fails; the internal child additionally cannot obtain bytes without its private owned-launch channel.

## Fail-closed launch and private raw broker

Perform checks in this order, with a denial receipt containing metadata only on failure:

1. Parse exactly the two official arguments. Require the exact official envelope under the approved artifact root and run/stage path; check schema, digest, initial running status, local target, clean commit, reviewed script and all frozen dependencies. Reject an empty fixture output, a recovered directory pretending to be fresh, undeclared files or conflicting active lock. Runtime source/model assets may be checked now; held-out external roots are still only lexical strings.
2. Resolve and authenticate the external approval; run `approval_check`; join the outer receipt; verify exact source/scope adoption and aggregate attempt ledger. Confirm this attempt is authorized, not consumed/completed, and its prerequisites match the logical DAG. Record the checked evidence and acquire the exclusive run/attempt lease. Fail before raw filesystem inspection if any item is missing, stale, mismatched or pending.
3. Materialize every planned unit/query and its initial missing status, including dependencies. Verify recovery metadata if applicable. Fix a monotonic deadline no later than the approval expiry and per-shard cooperative/outer caps. Enforce aggregate package time/attempt/disk bounds; the official per-manifest checker does not enforce an aggregate itself. No model download, remote compute or unplanned network fallback.
4. Create the scientific child suspended in the private kill-on-close Windows Job; verify assignment and receipt before resume. Establish a private inherited IPC channel bound to the verified process/Job identity, a fresh session nonce, exact attempt/core/index/schedule and output lease. Do not serialize a `ScopedCapability`, authorization boolean or reusable raw path into ordinary JSON/CLI/environment. The nonce only correlates this private session; it is not a substitute for approval.
5. The **parent broker** holds the in-process scientific capability and receipt allowlist. The child requests `(unit_id, source_uid, role)` over that channel; broker authorization precedes all I/O. Return the exact verified bytes or a declared failure, never a raw path to reopen. This reuses the existing `VerifiedBytes`/canonicalizer boundary. Fixture and scientific issuers are separate; a fixture marker, development receipt or forged child message cannot switch modes. Only the relevant scientific phase can request annotation bytes. Per-role size bounds come from the frozen index (the annotation exceeds the fixture's1MiB limit); do not broaden the fixture issuer.
6. For each permitted read retain existing regular-file, link/junction/reparse/hardlink rejection, final-handle containment before reading, bounded size, same-handle identity/mtime stability, exact SHA256 and final scope/expiry checks. Canonicalize the returned bytes with the frozen raw hash. Record raw-to-canonical receipt, then run the unchanged CandidateAdapter. Check lease, expiry and cooperative budget between units/checkpoints; deny new reads when expired and stop safely. Bytes already delivered do not authorize unlimited computation.
7. Journal raw/canonical/input/output/score/quality/seed/timestep/safety provenance and resource peaks. Child finalization produces declared artifact indexes even on normal cooperative failure. Parent verifies completeness/hashes, closes the Job, releases the lease and returns an honest status. Dispatcher finalization remains authoritative for its outer attempt record. A launcher return code or dispatcher `completed` alone never establishes a complete scientific inventory or a passing endpoint.

The parent broker is the single permission seam; do not add a second scientific raw reader inside the candidate or attack adapter. Private IPC and lifecycle checks are implementable without changing the official dispatcher. Their production issuer must remain unavailable until the real external trust/adoption adapter exists. Synthetic negative tests may mock that adapter only in the marked fixture path; they may not create scientific approval JSON or exercise real held-out paths.

## Bounded recovery without future hashes or renewed per-failure decisions

Freeze a logical attempt DAG before M1. For each shard enumerate its initial attempt and at most two same-code recovery alternatives with unique official run IDs. Their plans name only exact allowed predecessor attempt IDs, unit scope and the frozen core/runtime/source contract, not hashes of outputs that do not yet exist. Allow **at most two exceptional recovery launches across the whole approved package**, not two per source/shard. A shared atomic ledger enforces that global limit and the aggregate budget; an unused alternative is not an extra scientific replicate. Planned, explicitly budgeted checkpoint continuation across shards is separately enumerated in the normal DAG.

All alternative manifests can be computed now because their inputs are fixed metadata and deterministic recovery rules. The external approval packet lists every canonical manifest digest; one genuine human decision can cover that finite batch, with the authenticated controller supplying the required exact approval record for each selected manifest. Every official invocation still passes the unchanged exact-manifest check. No agent generates approvals; no manifest/config is rewritten to insert a future checkpoint hash or a convenient path. No automatic expiry extension is permitted.

At a recovery launch:

1. Authenticate its own approval/adoption/envelope as for a fresh run. Resolve only the plan's exact prior attempt directories beneath the frozen artifact root. Verify their execution manifests, official approval joins, core/runtime/source/index/schedule identities, parent DAG and terminal/inactive lease status. Never scan unrelated runs for a useful checkpoint or read arbitrary external resume paths.
2. Verify the append-only journal and artifact-commit entries independently. A usable checkpoint is a fully committed scheduled boundary (every10 optimizer updates, plus phase endpoints), with exact source/canonical/template identities, phase/step, latent and Adam states, all RNG state, numerical policy and dependency hashes. Commit the checkpoint file and its hash before the atomic journal commit marker. Ignore an uncommitted tail; a hash mismatch in a purported committed artifact is an integrity failure, not permission to fall back to an earlier favorable state.
3. Choose the latest complete boundary on the unique authorized predecessor chain by `(phase_order, step)`, independent of loss, image quality or detector outcomes. Preserve completed units and their original receipts; resume the first unfinished unit, restore the full state before any stochastic operation, and continue the frozen remaining updates. If there is no complete checkpoint, restart that unfinished unit from its frozen source/phase start with the same deterministic policy; retain and label the abandoned partial attempt. No changed optimizer, additional steps, seed, owner, source or best-checkpoint selection.
4. Before loading a checkpoint, rehash the actual retained bytes and emit a new **resolved-recovery receipt** with parent manifest/approval/journal/checkpoint byte hashes, complete commit sequence/step, resolution rule, logical scope, core and new attempt ID. This is an execution output, not an official-manifest input. The preapproved deterministic selector authorizes resolving these future hashes; the receipt makes the actual resolution auditable. It does not allow arbitrary data dependence or waive exact input identity.
5. Do not require the old outer `output_artifacts` array to list every checkpoint: dispatcher collection may not run after timeout/host loss. In that case the independently verified complete checkpoint/journal chain and exact prior official execution identity establish eligibility, with the outer attempt retained as incomplete/failed. Never relabel it completed or edit it. If it is still marked running after host loss, prove its process/Job lease is no longer live before adopting it; otherwise refuse concurrent recovery.
6. Merge by stable scientific unit/query ID and immutable lineage, never by best result or last writable filename. Negative/nonfinite/safety/invalid-input scientific outcomes remain outcomes; they are not infrastructure triggers to reroll. A changed raw hash, source roster, core or committed checkpoint fails validation and cannot be repaired by an automatic recovery. Propagate dependent missing rows and report conservative denominators. A later valid continuation can complete an interrupted trajectory while retaining its failed-attempt evidence and additional time/storage cost.

This explicitly proposes exact same-code checkpoint continuation as part of the **M1 batch recovery contract**; it does not silently reinterpret the older infrastructure-rerun allowance's failed-evidence reuse language. Scientific observation reuse here is limited to the unique unchanged trajectory and is disclosed at M1. The older allowance for up to two infrastructure-only code reruns is not permission to alter a preapproved manifest or bypass its separate conditions. This first contract needs no code-changing rerun path or new per-step reviewer: all execution/recovery code is frozen, rehearsed and included in the one independent M1 package review. A genuinely new implementation/manifest outside the listed batch must follow the applicable approval policy; do not invent a covered hash after the fact.
