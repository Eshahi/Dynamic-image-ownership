## Resolved software prerequisite

The existing Windows controller contains C1's full JSON Schema and cross-field validator; the clean WSL science environment lacks `jsonschema`. Rather than asserting Linux has validated a hand-constructed dataclass, `src/embedding/validation_bridge.py` provides an explicit exact-byte handoff. No environment/package/lock changes are needed. The production C1 validator, its schema and static-ID/scheduler checks remain unchanged.

The future trusted Windows parent will receive the already approved manifest from the official compute runner. Before starting a Linux child, it checks bounded, regular, non-linked manifest inputs with strict JSON, unique relative POSIX paths and exact hashes; requires the config, schema, validator, scheduler-reference and C1/bridge code; verifies that the actually executing installed validation sources match these snapshots. It invokes the existing **full** `load_method_config`, checks exact validated raw bytes/schema and run seed, rechecks input bytes after validation and exclusively creates `checkpoints/c4-config-validation.json` under that official run. Existing receipts are never overwritten or inferred to authorize a repeat.

The future Linux child rechecks every bound small input, actual validation/bridge code, canonical complete manifest hash, run/commit identities, complete input-digest mapping, exact raw config bytes and schema identity. It checks the parent's exact non-authorizing validator verdict and reconstructs the C1 snapshot only from matching reviewed bytes. A changed config, validator, run, seed, schema, expanded input inventory, linked path or added approval assertion fails closed before model import. Both ends preserve the explicit distinction between structural validation and scientific approval.

This is a **trusted reviewed code/provenance bridge, not cryptographic authentication**. An actor who can forge a self-consistent receipt, edit executing Python objects or compromise installed dependencies is not authenticated by these hashes. The official runner's exact clean commit/script hash and real user approval, filesystem/host trust and serialized reviewed launcher remain the trust boundary. The helper does not create a user verdict, validate the complete execution schema, verify actual Git cleanliness, or launch a process. Those are the official runner's responsibilities; this supplementary check does not replace them. The required dependency set covers this validation operation, not the complete future scientific worker.

Inputs are capped at two MiB each and 128 entries, with bounded reads and no external model/data root. The serialized receipt is separately checked against the same two-MiB read bound **before exclusive publication**; a structurally valid large config whose hex expansion exceeds the receipt limit is a retained resource/contract failure with no published receipt. The bridge imports no Torch, image decoder, learned model, dataset loader or network implementation. Config snapshots in tests are explicitly owned synthetic full-shaped schema fixtures; no actual `configs/c4-development.json` has been selected or added to Git. A future scientific config must bind genuine artifacts and justified parameters, not fixture digests or invented calibrations.
