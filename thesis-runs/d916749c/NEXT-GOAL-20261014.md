## Why the direction changes

The October 13-14 rounds (refinement ablation, lean variant, H1, FreqMark, RC1, the four instance descriptors DV1/CD1/BI1/FG128) produced no improvement. They share one formulation: a regenerated image must prove by itself, through the mark, that it is the same instance. Two measured facts limit that formulation:

- **Capacity.** The channel that survives regeneration delivers about 32 reliable bits. The 256-bit sketch (r3-256, 2026-10-06) failed, and FG128 only reached 17/18 by assuming 128 bits arrive intact.
- **Stability against discrimination.** No 32-bit instance descriptor was both regeneration-stable and specific:
  - CD1 kept 18/18 at .2 but accepted 4/6 sibling controls.
  - BI1 failed both ways.
  - FG128 matched the real pair 30/544.

The continuous information is still there. At .2 the native fine-feature cosine is .54-.79 for regenerated positives, against .016-.052 for the six siblings and .010 for pair 30/544. Squeezing it into a short self-carried code is what loses it. Your own scope memo (`research/journal-upgrade-20261009/e3-m1a-scope-decision.md`, "cheapest future contract experiment") already proposes `verify_instance(J, O, record)` with an enrolled reference. ## Step 2: registry-based verification (method change authorized for development)

### Design (fixed)

**Roles of the parts:**
- The robust semantic mark acts as a **pointer**: owner found, decoded q̂.
- The owner's **registry** holds one record per published marked image: owner, record ID, q, h and continuous descriptors of that image.
- Verification `verify_instance(y, O, registry)`:
  1. Run the unchanged detector for owner O; require semantic found and q̂ read.
  2. Fetch O's records whose q is within the method's native code radius of q̂.
  3. Compute the suspect's descriptors and the similarity with each candidate record.
  4. Accept the best record if its similarity ≥ τ.
- Registry full acceptance is F_R = pointer recovered ∧ record match.

**Descriptors, declared before outcomes (amended):**
- **D1 (primary):** E3's native fine-feature vector, `journal_fine_gaussian_instance.descriptor(...)['vector']`, uncompressed, normalized cosine.
  - In Claude's screen it alone separated every regenerated copy from every impostor and synthetic sibling: lowest positive .543 at .2 and .323 at .4; highest negative .057.
  - The similarity is content-driven: unmarked regenerations score alike.
- **D2 (secondary):** DINOv2-small final-layer CLS, already on disk at `MAIN/.thesis-build/assets/freqmark-reconstruction-20261013/dino` (revision `ed25f3a3`, Apache-2.0).
  - It separated real impostors but not the synthetic siblings (.99).
  - D2 becomes primary for 2b only if D1 fails the 2a kill rule and D2 passes it. Decide this now, not after outcomes.
- **D3 (descriptive):** the seven-view CLIP vector. It is expected to be weak for instance identity.

**Fingerprint-only arm (amended; required).** Run the same descriptors **without the pointer**:
- for each suspect, search all enrolled records (1:N) and accept the best record if its similarity ≥ τ;
- report correct-record identification, false accepts and N.

The question is what the watermark adds over a fingerprint database (compare DinoHash, arXiv 2503.11195). The screen shows D1 also finds regenerated copies of unmarked images.

**Regenerate-and-enroll scenario (amended; required).** This is attribution after T3 when a competing record exists:
1. An attacker regenerates the owner's published marked image (SD1.5 and SD2.1-base at .2 and .4).
2. The attacker enrolls the regenerated copy as their own record, under a different owner, in the same registry and later in time.
3. Query with the attacker's copy and with further regenerations of it.

Report correct-owner attribution for:
- **fingerprint-only:** two matching records; record whether only enrollment order could decide;
- **pointer plus registry:** the decoded pointer should still name the original owner.

The attacker does not re-embed a mark of their own; T6 is out of scope. This scenario is where the watermark's added value must show. If it does not, say so plainly.

**Disclosure.** Every report states the new side information: registry access, the per-record descriptor bytes, and lookup cost. It also states the limits: registry trust and availability, the privacy of stored descriptors, and candidate multiplicity per q (count it).
