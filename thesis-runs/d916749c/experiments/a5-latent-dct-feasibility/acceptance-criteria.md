# Acceptance criteria

## Design acceptance

This stage can be accepted only as an honest blocked design package if it:

- preserves all proposal-faithful method components and the scope guard;
- distinguishes a prospective feasibility hypothesis from an accepted result;
- records every missing method, data, statistical and execution input;
- provides measured GPU/disk observations where available, explicitly records unavailable RAM, labels every resource ceiling as provisional and non-executable, and records a zero approved external-spend ceiling;
- contains no executable script claim, invented hash, fabricated dataset identity, seed list, threshold, runtime or cloud price;
- receives independent read-only review with no unresolved blocking finding about those boundaries.

## Future preregistration acceptance

A future completed preregistration must add a reviewed A5 method/config freeze, immutable dataset manifests and leakage-safe splits, a justified primary endpoint and practical margin, independent sample-size calculation, fixed seed inventory, planned paired/domain-stratified comparison, uncertainty and multiplicity rules, and objective start/stop/exclusion rules. The hypothesis must be rejectable, and every failure must remain in the inventory.

## Future execution acceptance

Execution additionally requires a reviewed Python entrypoint accepting only `--manifest` and `--output-dir`, its SHA-256, an exact clean Git commit, input hashes, expected outputs, resource/duration/cost ceilings, a strict-schema-valid manifest, and a separate matching human compute approval. Remote execution remains unavailable through the current runner until its deadline-enforcement limitation is resolved and reviewed.

Negative or inconclusive results are retained and reported. They do not authorize threshold retuning, result-based exclusions, method substitution or a scope change.
